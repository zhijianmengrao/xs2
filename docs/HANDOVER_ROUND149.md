## 2. 为什么是这一轮

索引 §1 是「现在到哪」的唯一快照，五条数字行里有三条在 R137 被钉死，
余下两条一直有各自的「为什么可以手抄」：

- **文档体量**：「随轮次波动，钉死等于每轮强制改一次」（R146 §10.18 的
  边界原话）。但波动不等于不可判——它的**唯一合法值**就是磁盘语料的
  实时合计；每轮改一次不是成本，是记账。
- **代码基线**：它抄的是「main 上最后一次 CI 回写落在哪个提交」。这个
  事实在 `history.json` + `git log --grep` 里各有一份，手抄行是第三份，
  也是唯一可能撒谎的一份。

两条判据的锚都选在**已经存在且唯一**的第二份账上：体量锚磁盘语料，
基线锚写回账末条。判据不引入新的登记表，也不要求文档写得更细。

## 3. 实现

### 3.1 `tests/test_index_snapshot.py`（S4–S5）

| 判据 | 内容 | 锚点 |
|---|---|---|
| S4 | 体量行「N 行 / X MB」：N == 磁盘交接文档 `splitlines()` 总和；X == 归一化 UTF-8 字节 / 1 MiB（1 位小数） | 磁盘语料 |
| S5 | 基线行 `` `main` = `<sha>` ``：sha 是 history 末条 `ci-<id>` 的 bot 提交的**前缀**；行内「（R<n> …」== 该 bot 父提交标题里的轮次 | `history.json` + git bot 提交 |

实现要点：

- **归一化换行是跨平台前提**：`read_text()` 默认把 CRLF 读成 LF，再按
  UTF-8 编码计数。Windows 工作树（CRLF）与 CI 检出（LF）因此得到同一个
  字节数；若不归一，同一份语料会在两个平台上差出每个文件的行数。
- **MB 只判 1 位小数**：语料增删一行不该让「1.1 MB」在 1.05 附近翻成
  1.0/1.1 两个值。行数仍精确相等——它是可数的事实，不需要容差。
- **S5 的 sha 比较用前缀**：行内按仓库惯例写 7 位短 sha，判据要求它是
  bot 完整 sha 的前缀（至少 7 位），不要求行内抄全 40 位。
- **父提交轮次**从 `git log -1 --format=%s <bot>^` 的 `(R<n>)` 取；bot
  提交的父提交就是本轮提交（`feat(R149)` / `docs(R148)` 同形）。浅检出
  下 git 调用失败显式红，不降级成 skip（R136 的纪律）。

### 3.3 刻意不做的

- 不把 MB 精确到 2 位以上：语料增删与编码细节会让末位抖动，判据会变成
  「每次都要改」的噪声源；
- 不要求基线行抄全 40 位 sha：短 sha 是仓库既有写法，前缀校验已足够；
- 不判 bot 提交的**内容**（是否真的只改了 history.json）：那是 H 系与
  写回 e2e 的职责；
- 不扫交接文档正文里的历史数字：史料不参与当前时态。
