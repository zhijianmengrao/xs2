## 1. 本轮最重要的一件事：边界是曲线，不是「4000+」

R62 §9-5 记的是「仅当样本长到 4000+ 或失败率接近 50% 才需要」。本轮把这条
边界**逐点实测**出来，结论是它不可能是单一数字：

| 失败率（形状） | 直接求和开始抛 `OverflowError` 的样本量 |
|---|---|
| 3.92%（本项目当前形状） | **4317** |
| 5% | 3600 |
| 10% | 2200 |
| 25% | 1270 |
| 50% / 75% / 90% | **1030** |

**先更正记录，再讲结论**：R61 原文「n=4000 时 4% 形状仍可算（[3.50%, 4.55%]）」
是**对的**——那条形状的边界正是 4317，实测 4000 处仍可算。R62 把它抄成了
「4000+ 才需要处理」，于是只描述了曲线的一端。曲线的另一端（50% 形状）R61
另有一句「n=1100/k=550 溢出」，方向对、量级对，但没有取精确值。

所以本轮真正补上的事实是：**这个边界随失败率下降，最小值在 1030，而它恰好
出现在失败率很高的一端——也就是最需要判据说得出话的时候。** 一个「等样本涨到
4000 再处理」的处置，会让你在最该判红的那次事故里先拿到一段 traceback。

## 2. 第二件事：变异验证把「标准写法」证伪了，于是那段代码被删掉

第一版实现用了 max-shift 的 logsumexp（缩放求和），docstring 里写的是
「防止下溢」。变异验证里把它去掉——**153 条用例全绿**，与精确有理数的误差
仍在 1e-15 量级。

原因是可证的：求和项是二项 pmf，每一项都是概率，对数 ≤ 0，`exp` 回来 ≤ 1，
累加不可能溢出；下溢只发生在真实概率远小于 1e-308 的位置，那里返回 0 就是
正确舍入。缩放保护的是一个**在这里不存在**的失效模式。

于是删掉缩放，只留 `exp(log_term)` 逐项累加，并在 docstring 里写明「为什么不
需要」，把这次变异的结果写进去——否则下一个读到它的人会以为是漏写，再补回来。

这不是「少写了几行」的问题：这一段是本轮唯一有算术风险的地方，多一层机制就
多一处将来会被误以为「必须保留」的代码。

## 3. 第三件事：崩溃曾经冒充「政策突破」

`math.comb` 转 float 的 `OverflowError` 在旧代码里**没有任何捕获**，进程按
Python 默认以 **1** 退出——而 1 是「判了，结论是不合格」的退出码（政策超阈 /
回归 / per-workflow 超出）。两种完全不同的处置共用一个码：

- 1 → 查数据 / 查供应商；
- 崩溃 → 修判据。

CI 日志里两者的差别只有一行 traceback。R58 那条纪律（「同一退出码有多个来源
时，报告必须写明来源，否则两种处置会互相冒充」）在这里被违反了一次，只是没人
碰到过：入库快照 255 次尝试，距最近的边界（1030）还有 4 倍。

修法分两层：

1. **让算术本身变成全函数**：对数空间改写后，任何 `attempts/failed` 组合都
   给出一个有限值（有测试在四个样本量 × 六种形状上钉住）。
2. **边界上留一个只属于它的码**：`EXIT_NUMERIC_FAILURE = 8`，由
   `_run_judgement` 在六个派发分支上统一套用，只捕获 `ArithmeticError` 与
   `ValueError`。`TypeError` 之类的代码 bug 仍然照常崩掉——那是开发期信号。

## 4. 设计：一处算术 + 一处边界

1. `_binomial_cdf_le`：整条求和搬到对数空间。`comb`、`p**i`、`q**(n-i)` 各自
   取对数相加（pmf 的相邻比 `(n-i+1)/i * p/q` 递推），再逐项 `exp` 累加。
   用 `log1p(-p)` 而不是 `log(1-p)`：`p` 很小时后者会丢有效位。
   **单一路径**，不按 n 分「小 n 直算 / 大 n 换算法」——R55 的教训是两套式子
   迟早对同一个量给出两个答案。
2. `EXIT_NUMERIC_FAILURE = 8` + `_run_judgement(judgement)`：把「算不下去」
   与「判了且不合格」分开，六个派发分支（rate / regression / per-workflow /
   sample-size / stale / coverage / 默认判定）全部改走它。
3. 模块 docstring 的退出码清单同步补上 8。

## 11. 附：本轮在 CI 上撞到的一次 red——R63 的偏移预算只在共模假设下成立

`41077349717` 首跑时 ubuntu 的 e2e 步骤红了，失败的是 R63 那条形状判据：

```
[e2e] FAIL retry_backoff_long_chain_shape_is_honoured:
  第 1→2 段未递增：配置 [0.4, 0.8, 1.6]，实测 0.56s → 0.81s（比值 1.45，应≥1.5）
```

**与本轮改动无关**：`scripts/e2e_workflow_stub.py` 不 import 闸门脚本，同一份代码
在 20 分钟前的 `41076097743` 上 10/10 通过；重跑该 job 后又是 10/10（实测
`[0.405, 0.804, 1.605]`、偏移 0.005s、余量 80 倍）。这是一次**单段离群**。

但它是 R63 §3 那条限制的第一次实测证据，值得把数算出来。R63 的
`c_max = (b - r·a)/(r - 1)` 假定**同一偏移加在配对的两段上**（共模）。若偏移只落在
**前一段**上，预算就变成 `c_max = b/r - a`——对 2 倍递增、r=1.5 恰好**紧 3 倍**：

| 配置对 | 共模预算 | 只拖前一段的预算 |
|---|---|---|
| 0.4 → 0.8 | 0.400s | **0.133s** |
| 0.8 → 1.6 | 0.800s | 0.267s |
| 1.6 → 3.2 | 1.600s | 0.533s |

这次实测第一段偏移 **0.16s**（0.56 − 0.40）、第二段 0.01s——**超过 0.133s 那条线
1.2 倍**，于是比值掉到 1.446。换句话说：R63 写进输出的「偏移预算 0.40s/段」
在共模假设下是对的，但**判据真正的弱点是单段离群，而它对首段的预算是 0.133s，
不是 0.40s**。R63 的「余量 25–67 倍」是拿共模中位数与该预算比，不能用来说明
这条判据对单段抖动有同样的余量。

本轮不修（范围只做主线收口）。修法有两个方向，留给下一轮拍定：
1. 把预算改成**逐段**的：每个测得的段各自判 `≥ 配置 ± c_max`，而不是只判相邻
   比值——这样单段离群会被定位到具体哪一段，而不是伪装成「形状不对」；
2. 每个形状场景重复 N 次取中位数再判——代价是 e2e 时长线性增长，且要重新回答
   「N 次里几次算通过」。
