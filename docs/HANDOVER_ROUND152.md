## 2. 满窗滚动：判据第一次走到自己的边界

history 的保留期是 80 条（R112 拍板），`record` 的写入是
`history[-80:]`——追加后裁掉最旧的。R149 开工时 78 条，R149/R150 的
写回各追加一条，到 R150 满格；R151 的写回是 **第一次裁剪**。

裁剪对两份「第二份账」的影响：

| 判据 | 旧口径 | 滚动后的错误 |
|---|---|---|
| D2 | 写回序号 B == 该 run 在**当前** history 里的下标 | R149 §6 的 `78→79` 看起来「错」：它现在在第 78 条；R150 的 `79→80` 同理。两条声明在写回当时都是真的 |
| H3 | git bot run id 集合 == 当前 ci 条目集合 | R152 树还能相等（80/80，裁掉的是一条 legacy 种子）；R152 自己的写回之后就是 81 bots vs 80 条目——从 R153 起必红 |
| H1 | 时间戳形状的 legacy 种子**恰好 1 条**且在第 1 条 | R151 的裁剪把种子裁掉后，R152 树一条都没有——旧 H1 必红 |

这不是「判据太严」，是判据的锚选错了：写回序号是**当时**的事实，集合
恰等只在**窗口未滚动**时成立。窗口是配置，不是账本的一部分。

## 3. 实现

### 3.1 D2：按 bot 提交当时的 history 快照

`tests/test_handover_ci_backfill.py`：

- `_history_at_bot(run_id)`：`git log --grep "record CI run <id>"` 找 bot
  提交，`git show <bot>:tests/fixtures/e2e_retry_history/history.json`
  取当时快照；同一 run 的快照在进程内缓存。
- §6 的每个 run id 必须出现在**它自己的**快照里（而不是当前文件）。
- `A→B`：B == 该 run 在快照中的 1-based 下标，A == B-1。
- **满窗后写回计数不再递增**，§6 改写「第 N 条」；D2 同时认这种写法，
  N 同样按快照判。R151 §6 是第一个使用该写法的轮次。
- 浅检出下 `git log` / `git show` 失败显式红，不降级成 skip（R136）。

### 3.2 H3：按序后缀

`tests/test_history_ledger_accounts.py`：

- bot 提交的 run id 按 `git log --reverse` 取**从旧到新**的序列。
- 当前 history 的 ci 条目序列必须等于该序列的**最新 N 条、同序**。
- 错误信息同时报「缺 / 多 / 错位（位置, history, bot）」，双向发声音。

### 3.3 H1：legacy 种子可被裁掉

`tests/test_history_ledger_accounts.py` 的 H1 原判据要求时间戳形状的
run_id **恰好 1 条**且在第 1 条。窗口滚动后种子会自然消失；判据改为
**至多 1 条**、若存在则只能是第 1 条。它仍然防止新条目再以时间戳入库
（第 2 条起出现非 ci- 形状即红），只是不再要求历史必须永远带着种子。
