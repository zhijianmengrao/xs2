## 2. 为什么是这一轮

双语 README 是两处独立的写入点：中文加一节、英文忘了加，没有任何命令
会报错，读者只会看到两份「长度不同」的说明。R149–R152 把索引 §1、双锁
与 Python 支持面变成机判后，展示层还剩这个余项（R152 §7 登记）。

| 结构面 | README.md | README.en.md | 判据 |
|---|---|---|---|
| Markdown 标题 | 25（11 H2 + 14 H3） | 24（11 H2 + 13 H3） | 无 |
| 代码块 | 5（10 行围栏） | 5（10 行围栏） | 无 |
| 显式锚点 | 6 | 6 | 无 |

「10 个代码块」的口径先纠一次：R152 §7 数的是围栏行（每块两行），
真正配对后的块数是 5。M3 按配对后的块计数，并比对开头围栏的语言标签
序列——块数相同但语言顺序不同，同样是结构漂移。

## 3. 实现

### 3.1 `tests/test_readme_parity.py`（M1–M4）

逐行扫描，带围栏状态机：

- 围栏内的一切都不算结构（代码块里的 `#` 注释不会被误认成标题，
  `<a id>` 也不会被误收）；
- 结束围栏必须只由反引号组成且不短于开头围栏；到文件末尾仍未闭合
  显式红（不静默把剩余内容当成结构）；
- 标题只认行首的 H2–H6（两份文档的 H1 都是顶部 HTML `<h1>` 品牌图，
  不在 Markdown 标题序列里）；
- 锚点只认显式的 `<a id="…"></a>`，GitHub 自动生成的标题锚点不在射程
  （标题文本本就不同）。

| 判据 | 内容 | 锚点 |
|---|---|---|
| M1 | 两份文件存在且非空；都能解析出 H2/H3、代码块与锚点；围栏必须闭合 | 语料 |
| M2 | H2–H6 的层级序列逐项相等（个数与顺序） | 标题层级 |
| M3 | 代码块个数与开头围栏的语言标签序列逐项相等 | 围栏 |
| M4 | 显式锚点 id 序列逐项相等，且每份文件内不重复 | `<a id>` |

M1 是语料守卫：任何一处解析为空都在此红，防止 M2–M4 在空序列上空转。

### 3.3 刻意不做的

- 不比对标题文本——两份文档语言不同，只比对层级序列；
- 不要求逐段翻译对应（英文是面向国际读者的改写，不是逐字译本）；
- 不比对代码块内容（安装命令按平台/语言改写）与围栏外的 HTML 表格、
  徽章；
- 不要求每个代码块都有语言标签，只要求两份的标签序列相同；
- 不把 GitHub 自动标题锚点纳入 M4（标题文本不同，自动锚点必然不同）；
- 不判 README 的轮次/版本叙述——那是活文档盖子与版本发布判据的范围。
